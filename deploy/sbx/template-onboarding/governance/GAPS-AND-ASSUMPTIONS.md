# Gating and provenance for MOCA templates: gaps and assumptions (working record)

> **Preview.** The gating and provenance register is implemented but not yet declared Stable;
> interfaces and limits may change. Known limits: this page.

From sbx-template, started 2026-11-02. A living register for the SWE-bench-at-scale work: what is
missing today for image and template gating and provenance, and the assumptions we are working
under. Each entry has an id so the spec, the code and the validation can cite it.

Sources: the inventory [`INVENTORY-2026-11-02.md`](INVENTORY-2026-11-02.md) (MOCA at sbx-template 22e19036), the
2026-10-31 and 2026-11-01/02 bm1 runs, image-factory's records, and the user's decisions below.

## Gaps: gating (G)

| Id  | Gap                                                                                                                                                                                                                                                                                    | Evidence                                               | Severity for D5                              |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------- |
| G1  | No written MOCA gating rule set: rules are spread over build scripts, worker start, the installer and docs                                                                                                                                                                             | inventory §1-2                                         | blocking (D6: image-factory writing it)      |
| G2  | No signature, attestation or origin check on a sandbox image; `--registry` accepts any host; no registry allowlist                                                                                                                                                                     | inventory §3, gap 3                                    | high                                         |
| G3  | image-factory's gate evidence (`source_record_digest`, `proved_in_vm`, gate result) is carried in the spec but never verified                                                                                                                                                          | inventory §3                                           | high                                         |
| G4  | Default images outside templates are mutable `:latest` (build-rootfs default, the container tier of P6, the process-manager runtime, and the Dockerfile base)                                                                                                                          | gaps 1-2                                               | medium (templates already pin a digest)      |
| G5  | `skip_git_identity_check` (commits refused on purpose) records no reason, and nothing checks that commits ARE refused when a spec says so                                                                                                                                              | gap 10; bm1 2026-10-31 (a63ec740 let SWE-bench commit) | high for SWE-bench                           |
| G6  | "The probe uses public targets only, never grading tests" is documented, not enforced                                                                                                                                                                                                  | gap 12; `ONBOARDING.md`                                | high for benchmarks                          |
| G7  | No scan for secrets or keys in the image (only the `--egress-ca` file), no setuid, size, vulnerability or SBOM check                                                                                                                                                                   | gap 11                                                 | medium                                       |
| G8  | The template tool rule ("bash, git, tar, ripgrep") is enforced through `build-rootfs.sh`'s list, which omits tar and requires gh                                                                                                                                                       | gap 9                                                  | low                                          |
| G9  | The probe is not re-run after deployment (the worker's start-up probe runs `true`)                                                                                                                                                                                                     | gap 12                                                 | medium                                       |
| G11 | **Regression (2026-11-02):** upstream 494353b7 (merged into sbx-template as 22e19036) added `gh` to `build-rootfs.sh`'s REQUIRED_TOOLS; no image-factory image has gh, so `template-build.sh` at 22e19036 would refuse them all. Earlier builds passed because their trees predated it | image-factory's question, 2026-11-02                   | blocking for any build at head               |
| G10 | The container tier gates nothing at run time (capabilities probed from PATH, no digest check)                                                                                                                                                                                          | gap 8                                                  | out of scope for microVM templates; recorded |

## Gaps: provenance (PV)

| Id  | Gap                                                                                                                                                                                              | Evidence          | Severity for D7-D8        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------- | ------------------------- |
| PV1 | No provenance store at all: the facts are in files on the build host and in operator notes                                                                                                       | —                 | blocking                  |
| PV2 | The snapshot manifest is not authenticated; capabilities, image, instance type, guest size, vcpus and the egress CA sit outside its `hash`; the Go `Manifest` lacks vcpus and `egress_ca_sha256` | gap 4             | high                      |
| PV3 | vmstate and memfile are not hashed (a documented choice for speed)                                                                                                                               | gap 5             | medium (needs a decision) |
| PV4 | The template record is unsigned; worker start does not check the record's `manifest_hash`, nor the image digest in `/etc/moca-rootfs-source`                                                     | gap 7             | high                      |
| PV5 | The record lacks the chain: image-factory's record digest and gate result, the MOCA commit, the builder, the probe's result                                                                      | 2026-11-02 review | high                      |
| PV6 | Deployment is not tracked: register, attach (activate), detach, retire, who and when, live only in step lists and chat                                                                           | 2026-11-02 review | blocking for D5           |
| PV7 | A run cannot be traced to its exact build: a session or sandbox reports its template, not the snapshot's manifest hash                                                                           | 2026-11-02 review | high                      |
| PV8 | The instance-type check fails open and has an environment override                                                                                                                               | gap 6             | low                       |
| PV9 | Nothing in the control plane holds provenance today; Redis is not persistent storage for it                                                                                                      | D8                | blocking                  |

## Assumptions (A)

| Id  | Assumption                                                                                                                                                                                                            | Why we make it                                                                                   | Revisit when                                     |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| A1  | Clients are admin clients (the existing `admin` role from `SH_ADMIN_SUBJECTS`)                                                                                                                                        | D10                                                                                              | the authorization design                         |
| A2  | One worker serves one template (one snapshot), as today                                                                                                                                                               | it is deliberate in the session-templates spec; merging would not save the pinned memfile memory | a measurement shows per-worker overhead matters  |
| A3  | A host holds about 26 SWE-bench templates on disk, and memory for about 36 attached workers, at 4 GiB guests                                                                                                          | measured on bm1, 2026-11-01/02                                                                   | a host of another size                           |
| A4  | "Active" means: snapshot on disk, worker attached; the active limit is set by memory and disk per host                                                                                                                | A3                                                                                               | lazy memfile pinning (plan item E)               |
| A5  | Snapshot builds and gating stay operator-side (or an approved build service); clients request them, never run them                                                                                                    | D9                                                                                               | —                                                |
| A6  | image-factory's gate (guest emulation, network none, read-only root, commits refused) is the evidence for its images, and its records are the source of their image provenance                                        | D6                                                                                               | image-factory's rule set                         |
| A7  | Provenance records are append-only, each naming its predecessor by hash, signed by the control plane; verification needs only the records and the public key                                                          | D7-D8                                                                                            | the spec review                                  |
| A8  | The control plane needs a persistent store for provenance (a volume or a database), separate from Redis                                                                                                               | D8, PV9                                                                                          | the spec review                                  |
| A9  | Images are referenced by digest only; a tag is never a template's image                                                                                                                                               | already enforced by `template-build.sh`                                                          | —                                                |
| A10 | SWE-bench templates have no network and refuse agent commits; their probe is a public test target                                                                                                                     | image-factory's rule D2; the user's 2026-10-30 rules                                             | —                                                |
| A11 | The control plane is on ykt3 (OpenShift) and the workers on a KVM host (bm1) for the validation                                                                                                                       | today's deployment                                                                               | —                                                |
| A12 | autobench-moca moves its pinned MOCA only between TB batches, and only to a tag of sbx-template                                                                                                                       | its rule                                                                                         | —                                                |
| A13 | The first validation uses a scripted mock model; a real model run needs the user's OK and announcing spend to autobench-sandbox                                                                                       | cost and the shared budget                                                                       | —                                                |
| A14 | ~~No automatic deactivation~~ superseded by A16                                                                                                                                                                       | —                                                                                                | —                                                |
| A16 | **Aging and replacement:** an aging policy deactivates a template idle past a limit, and when the active limit is reached a new activation replaces the template least recently used (by its latest timestamp of use) | the user, 2026-11-02 (answers Q1)                                                                | the spec sets the limit and what counts as "use" |
| A15 | Feasibility first: no hardening (rate limits, multi-host scheduling, HA) in the first version                                                                                                                         | D10                                                                                              | after the validation                             |
